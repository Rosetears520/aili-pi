## Purpose

让 `sub` 保持唯一正式委派入口：默认使用 Pi；只有当前用户明确指定外部 CLI 时，才由可见 Herdr pane 中的 Pi Agent 通过受控、help-first、非交互 runner 调用该 CLI，同时从 AILI 插件组合中移除冲突的 ACP delegation 工具。

## ADDED Requirements

### Requirement: Omitted CLI always uses normal Pi execution
A `sub` request that omits `cli` SHALL use the existing Pi execution path, model/thinking resolver, backend settings and Agent lifecycle. Catalog visibility, task wording generated by the model, prior turns and persistent artifacts MUST NOT select an external CLI.

#### Scenario: User asks for a subagent without naming a CLI
- **WHEN** the current user message requests a subagent but does not explicitly name a registered external CLI
- **THEN** the Parent omits `cli` and dispatch remains ordinary Pi execution

#### Scenario: Prior turn used an external CLI
- **WHEN** a prior turn used an external CLI but the current user message does not name one
- **THEN** the current turn receives no external CLI authority and the previous `cli` value is not reused

### Requirement: External CLI selection requires exact current-turn user authority
The public `sub` schema SHALL accept an optional canonical `cli` identifier. A non-empty `cli` SHALL be accepted only when the corresponding current `interactive|rpc` user input explicitly names that CLI for subagent use. Availability or registration SHALL NOT constitute authorization.

The first supported registry SHALL recognize unambiguous product phrases for `claude-code`, `gemini-cli`, `codex-cli`, `opencode`, and `grok-cli`. Ambiguous provider/model words such as `Claude`, `Gemini`, `Codex`, or `Grok` without `Code`/`CLI` context MUST NOT select an external CLI.

#### Scenario: User explicitly requests Claude Code
- **WHEN** the current user message says to use Claude Code for the selected subagent
- **THEN** the Parent may pass `cli: "claude-code"` for that turn

#### Scenario: Model adds a CLI without user authority
- **WHEN** the current user message does not authorize an external CLI but a model-generated `sub` call supplies `cli`
- **THEN** preflight rejects it before durable allocation and explains that CLI availability does not grant authority

#### Scenario: User mentions a provider ambiguously
- **WHEN** the user says `Claude`, `Gemini`, `Codex`, or `Grok` only as a model/provider reference
- **THEN** the system does not infer an external CLI

### Requirement: Explicit external CLI runs as a nested tool inside a Pi Herdr Agent
The first release SHALL keep `driver: pi-cli`. For a new Agent with an authorized `cli`, one atomic preallocation step SHALL validate CLI authority, derive Herdr, verify Herdr availability plus role/effective-bash eligibility, and freeze backend/loadout before any support check or durable allocation. The external process SHALL be a nested command launched by the Pi Agent's existing bash/tool policy and SHALL be recorded separately as `nestedCli`.

The Herdr pane SHALL display the Pi TUI and its tool execution; the system SHALL NOT claim that the external CLI's native interactive TUI owns the pane.

#### Scenario: New Agent requests an external CLI
- **WHEN** an authorized new `sub` request supplies `cli`
- **THEN** it is allocated on Herdr with `driver: pi-cli`, the runner modifier and the canonical `nestedCli` audit value

#### Scenario: Existing managed Agent requests an external CLI
- **WHEN** a continuation targets an Agent whose frozen backend is managed and supplies an authorized `cli`
- **THEN** preflight rejects the request and instructs the Parent to create a new Herdr Agent rather than switching the existing Agent backend

#### Scenario: Existing Herdr Agent receives an authorized CLI turn
- **WHEN** a continuation targets a Herdr Agent and the current user explicitly authorizes a registered `cli`
- **THEN** that turn may attach the one-shot runner while preserving the Agent's Pi Driver identity

#### Scenario: Selected role cannot run bash on Herdr
- **WHEN** an authorized CLI request targets a role that is not Herdr-eligible or lacks effective bash capability
- **THEN** preflight fails before allocation and does not substitute another role

### Requirement: External CLI runner is help-first and non-interactive
Before invoking task execution, a deterministic package-owned probe helper SHALL resolve only allow-listed executable basenames for the canonical CLI, run `--version` then `--help` without shell interpolation, apply a 5-second timeout to each probe, cap their combined UTF-8-safe output at 64 KiB, terminate the process group on abort/timeout, and return bounded structured evidence. Grok's generic `grok` candidate SHALL be accepted only when bounded version/help identity markers establish the intended product; ambiguity SHALL fail.

The Pi Agent SHALL receive that frozen help plus an immutable built-in modifier and SHALL select only a one-shot non-interactive invocation visibly supported by the installed help. AILI SHALL NOT implement automatic install/update/login/browser-auth, known permission-bypass flags, interactive TUI takeover, shell-profile sourcing, explicit external session resume or recursive delegation. A missing executable, malformed/unsafe help, authentication blocker or missing usable non-interactive mode SHALL fail explicitly. The final argv remains subject to the Pi Agent's existing bash permission/tool path.

#### Scenario: Installed CLI has a supported non-interactive mode
- **WHEN** the allow-listed executable exists and its current help advertises a supported one-shot non-interactive invocation
- **THEN** the deterministic probes complete first and the Pi Agent may invoke a help-supported mode in the authorized task cwd through its existing bash permission path, reporting bounded output and exit status

#### Scenario: CLI is missing
- **WHEN** no allow-listed executable candidate exists
- **THEN** execution fails without installation and reports the expected executable candidates

#### Scenario: Help does not advertise a safe mode
- **WHEN** the installed version's help exposes no supported non-interactive mode
- **THEN** the runner refuses to guess flags or take over the pane interactively

#### Scenario: CLI requests authentication
- **WHEN** the external CLI cannot proceed without login or browser authentication
- **THEN** the runner stops and reports the blocker without starting an auth flow or persisting credentials

### Requirement: External CLI use remains inside existing permission and task scope
Explicit CLI selection authorizes calling that named CLI for the current task only. Per the accepted first-release policy, it also authorizes that CLI to use its existing vendor-specific login/config/cache in normal user HOME and to perform the provider network/source transmission inherent in the requested CLI task. AILI SHALL NOT copy, parse or expose those credentials and SHALL disclose that vendor-internal HOME writes, token refresh, cache/session behavior and network destinations are not inspected by AILI.

This authority SHALL NOT extend to unrelated Git, publication, destructive or non-CLI user-home operations. The nested process SHALL inherit the Herdr Pi child's cwd and existing bash permission/sandbox boundary for enforceable local launch/filesystem/process controls; unavailable required capabilities SHALL fail closed.

#### Scenario: CLI launch or local filesystem operation exceeds the enforceable boundary
- **WHEN** the nested process launch or a locally sandbox-visible filesystem/process operation exceeds the effective Pi bash permission boundary
- **THEN** that enforceable operation is denied or the turn fails; vendor-internal network/source behavior remains disclosed rather than claimed as inspected

#### Scenario: External CLI turn settles
- **WHEN** the one-shot CLI process exits
- **THEN** structured audit records bounded probe identity/version/completion while the Pi Agent may report final command output/exit as model-reported evidence; neither surface exposes credentials or raw protected paths, and vendor-local cache/session writes are not treated as AILI Agent continuation state

### Requirement: AILI-owned ACP delegation is permanently disabled
The AILI-owned billion-context composition SHALL set delegation disabled as a locked adapter decision. Global or project `acp.json` SHALL NOT re-enable delegation when the factory explicitly disables it.

The AILI composition SHALL NOT register `acp_delegate`, `acp_delegate_wait`, or `acp_delegate_cancel`, inject ACP delegation prompt text, or activate its delegate status widget. It SHALL continue to provide the owned context/compression tools and hooks.

#### Scenario: AILI package starts with no user ACP config
- **WHEN** the AILI-owned context extension starts
- **THEN** only compression/context tools are registered and no ACP delegation surface exists

#### Scenario: User ACP config sets delegate true
- **WHEN** global or project `acp.json` contains `delegate: true` but the AILI factory explicitly disables delegation
- **THEN** the AILI-owned extension remains delegation-disabled

#### Scenario: Compression remains available
- **WHEN** ACP delegation is disabled
- **THEN** `compress`, `decompress`, `search_context`, `acp_status` and the selected context owner continue to function unchanged

#### Scenario: Separate third-party Extension registers delegation
- **WHEN** a user independently installs another Extension that registers its own delegation tools
- **THEN** that separately owned Extension remains outside the guarantee of this package and AILI does not globally suppress unrelated tools
